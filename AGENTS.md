# Agent development guide — TrackRank

Applies to this repository. Read this before changing code. More-specific instructions in subdirectories apply to their scope.

## Start here

1. Read `README.md` and `docs/ARCHITECTURE.md`; inspect `git status` and the code paths relevant to the task.
2. Read the applicable reference: `PRODUCT.md`, `docs/API.md`, `docs/AUTHENTICATION.md`, `docs/PLANS.md`, or `docs/BILLING-OPERATIONS.md`.
3. Preserve existing user changes. Do not reset, discard, overwrite secrets, or rewrite unrelated files. Keep changes focused; avoid whole-file formatting during functional edits.
4. Follow the task through implementation, appropriate verification, and a clear handoff. Distinguish implemented, locally tested, staging-verified, and deployed results. Never claim an external journey passed from mocks alone.
5. Review and update `AGENTS.md` and `README.md` in the same change whenever deployment, local setup, self-hosting, or an app-wide convention changes. Record the convention contributors must follow in `AGENTS.md` and the steps or behavior users and operators need in `README.md`. Keep linked reference docs in sync where their instructions change. Include this review before calling the task complete.

## Stack and code map

- TypeScript / React 19 / TanStack Start and Router / Vite. Cloudflare Workers hosts the app; D1 stores metadata, private R2 stores raw evidence, Workflows executes runs, and Cron dispatches/reconciles work.
- `src/routes/`: pages, onboarding and authenticated UI. `src/components/ui/`: shared shadcn/Radix primitives. `src/styles.css`: shared styles. Use `PRODUCT.md` for audience and workflow decisions. Follow the evidence presentation, accessible controls, mobile navigation and record identity conventions in `docs/DESIGN.md`.
- `src/worker.ts`: HTTP routing, auth/API/MCP/webhook entry points and scheduled work. `src/server/types.ts`: environment bindings and shared helpers.
- `src/server/api.ts`: REST routes, validation and tenant authorization. `mcp.ts`: MCP tools and agent-facing schemas.
- `auth.ts`, `auth-schema.ts`, `local-auth.ts`: identity, roles, invitations and tightly scoped local verification bypass.
- `provider.ts`, `dispatch.ts`, `workflow.ts`, `scheduler.ts`: provider payloads, run admission, durable execution, callbacks and recovery.
- `prompt-batch.ts`, `bulk.ts`, `provider-options.ts`: batch prompt settings, independent samples, schedules and supported provider options. `src/lib/prompt-input.ts`: paste parsing.
- `provider-credentials.ts`: organization-scoped credential updates and per-provider removal. `run-history.ts`: shared history and research filters. `resource-archive.ts`: workspace, prompt and brand deletion behavior.
- `plans.ts`, `trials.ts`, `billing.ts`, `rate-limit.ts`: versioned entitlements, trials, Stripe lifecycle and quota enforcement.
- `operations.ts`, `erasure.ts`, `crypto.ts`: operator-only maintenance, deletion and encryption. Treat changes here as security-sensitive.
- `migrations/`: ordered D1 SQL migrations. `tests/`: Node test suite with isolated SQLite fixtures and mocked external services. `scripts/`: setup, environment-specific deployment and opt-in acceptance tools.
- `src/routeTree.gen.ts` is generated by the router/build tooling; do not hand-edit it. Do not commit build output, local state or private fixture files.

## Local development

Use Node.js 22.13+ (Node 24 recommended) and npm with the committed lockfile:

```sh
npm ci
npm run setup:local
npm run dev
```

Local setup uses `wrangler.local.jsonc`, applies local migrations, and preserves existing `.dev.vars` secrets. Default URL is `http://localhost:3000`; `BASE_URL` and the actual dev-server port must agree. Read `README.md` before changing ports or testing auth. Do not use hosted resource bindings for scratch development.

Local account creation and UI exploration need no paid provider credentials. Real collections require organization-owned provider credentials in Settings and incur provider costs. Setup, saving prompts and saving paused schedules must not launch collections.

## Implementation conventions

- Ship every new, changed, or removed user-facing capability across the UI, REST API, and MCP in the same change. Every action a user can perform in the UI needs an equivalent agent workflow, including reads, writes, bulk operations, and management actions. Add or update the REST routes, discoverable MCP tools and schemas, and `docs/API.md` before calling the feature complete.
- Reuse the same server operations and validation across these surfaces. Apply equivalent organization scope, roles, entitlements, and usage limits. Give privileged agent actions explicit authorization scopes and preserve any required user confirmation or verified handoff.
- Reuse existing server helpers, schemas and UI primitives. Prefer small cohesive modules over adding more unrelated logic to the main app/API files. Keep secrets and server-only imports out of browser bundles.
- Validate untrusted input with strict schemas, bounded lengths/counts and supported enumerations. UI dropdowns do not replace server validation.
- Put exact bulk/static routes before generic item routes so names such as `bulk-settings` are not interpreted as resource IDs.
- Every tenant resource lookup and mutation must be organization-scoped. Validate all selected IDs before a batch write; reject foreign/missing IDs without partial changes. Preserve session roles, API-key scopes and read-only viewer behavior.
- Keep authorization, plan eligibility, minute rate limits and monthly run quotas server-side. Bulk operations share per-run accounting. Show users total runs and separate provider costs.
- Use workspace-owned prompt sets and current tags for live reporting. Moving or archiving prompts clears their set memberships in D1. Preserve historical run workspace and brand snapshots. Use the shared server history scope for Overview totals and daily trends, research, run lists and CSV. Never derive Overview metrics from paginated browser rows.
- Preserve raw provider evidence and normalization semantics. Keep organic Google results separate from AI answer citations/mention metrics. Missing AI Overviews and failed runs are not successful AI answers.
- Use supported engine location/language values. Refresh the public catalog with `scripts/refresh-provider-options.mjs` when needed; credentials belong in the execution environment, never in the catalog or Git.
- Use the shared form layouts in `docs/DESIGN.md` when pairing fields with actions. Use accessible labeled controls, keyboard-operable tooltips, loading/error/empty states, and the existing responsive light-default design (dark is explicitly opt-in). Authenticated views show actual data, not invented metrics.
- Give new authenticated sections and shareable records a stable URL that restores the same organization, workspace, and destination after sign-in or reload. Follow the shareable navigation guidance in `docs/DESIGN.md`.
- Apply the global workspace selection to research drill-downs. Match domains, URLs and grounding queries against stored evidence from eligible AI answers. Link each match to its run and show brand mentions from the run snapshot.
- Keep provider credentials, organization management and hosted billing in Settings. Use organization-scoped Settings links for Providers, Team & access, and Billing. Keep billing accessible when workspace access is paused. Show credential status and add, replace and remove actions per provider. Removing DataForSEO pauses collection schedules. Removing OpenRouter preserves collection schedules.

- Use the workspace-owned prompt set for the **Tracking** list and detail. Preserve the set’s organization, workspace, and active view when linking to questions, schedules, or evidence. Summarize schedule state per variant. If a variant has multiple schedules, any enabled schedule makes the variant scheduled.

## Durable execution and data changes

- Provider submission can spend money. Never blindly retry an accepted or uncertain submission. Correlate batch acknowledgments and callbacks to stable run/task IDs. Preserve per-run submission claims, durable polling, bounded recovery and explicit uncertain states. Advance the schedule cursor in the same D1 batch as run admission.
- Each requested sample has its own stable identity; replaying the same batch must not create more runs. Keep shared-settings updates partial: changing enabled state must not reset repetitions, time slots or other unspecified settings.
- Split large run and schedule actions into bounded requests. Enforce monthly run allowance at admission. Preserve request keys and per-run identities across retries. Page Workflow launches in groups of up to 100 and keep unstarted runs eligible for Cron.
- Use stable schedule batch IDs when creating schedules across requests. Page schedule listing and due-run processing independently of the saved batch size. Provider limits apply during dispatch.
- Add ordered migrations rather than editing already-applied migrations. Before launch, replace obsolete API and storage shapes with one supported path. Coordinate schema cutovers with Worker deployments and preserve admitted run identities. Update affected test fixtures.
- Workspace and prompt deletion archives the records and removes their schedules. Keep existing run links, raw evidence and historical brand snapshots available.
- Never casually rotate `CREDENTIALS_KEY` or `AUTH_SECRET`; existing encrypted credentials/sessions depend on them. No secrets, cookies, bearer URLs, private database exports or `.local` fixtures in logs, reports or commits. Sanitize acceptance evidence.

## Verification and handoff

For application changes, run the relevant tests and required checks:

```sh
npm test
npm run build
npm run typecheck
```

- Add meaningful regression coverage for changed behavior: tenant boundaries, quota admission, idempotency, lifecycle transitions and partial updates where applicable. Do not add implementation-mirroring tests or rerun broad suites for documentation-only edits.
- Verify new or changed user actions through the REST endpoint and an actual MCP tool invocation, including permissions and error behavior where relevant.
- Inspect changed UI in a browser, including bulk selection, Advanced controls, errors and responsive behavior as relevant. An HTTP200 alone does not prove a working interaction.
- `scripts/local-smoke.py` is opt-in, loopback-only and leaves disposable local data. `npm run test:billing:lifecycle` is opt-in and creates Stripe TEST resources; it is not part of the offline suite. Read the scripts before running acceptance tools.
- Real OAuth/email/invitation/provider/scheduled-workflow acceptance is separate from mocked tests. Do not create fake production users, enable paid schedules, send messages or incur provider charges merely to make a test pass.
- Review `git diff --check` and staged contents before committing. Keep secrets/private state ignored. Use a focused branch/commit and the repository PR/CI workflow for code changes; report blockers and remaining manual checks explicitly.

## Environments and releases

- Local: `wrangler.local.jsonc`. Staging: `wrangler.staging.json`. Hosted production: `wrangler.jsonc`. Self-hosting uses the separate `*:selfhost` commands and owner-supplied configuration; see `docs/SELF_HOSTING.md`.
- `npm run deploy:staging` and `npm run deploy:production` rebuild for their target and verify generated Worker/D1 bindings. Do not deploy a stale build or bypass these environment guards. `npm run deploy` targets hosted PRODUCTION, not a preview.
- Deployment and remote migrations require task authorization. Read `docs/BILLING-OPERATIONS.md` for backup, migration, rollback, recovery and release checks. Preserve existing resources/secrets and verify the deployed environment afterward. CI checks do not automatically deploy.
- Apply pending D1 migrations with the explicit target configuration before deploying Worker code that relies on them. Apply migrations `0016` through `0018` in a coordinated cutover because older Workers require the removed schema. Apply migration `0019` before deploying durable collection dispatch and `0020` before deploying prompt tags. Apply `0024` before deploying prompt sets and server-side Overview analytics. Apply `0026` in maintenance with the matching Worker because it removes the prompt-level execution flag. Apply migration `0027` in a coordinated cutover before deploying shared prompt questions.
- Publish hosted offers in D1 only after the pre-enable checks and tax review in `docs/BILLING-OPERATIONS.md`. Keep Stripe Price mappings immutable and deployment-specific. Checkout follows the owner-approved Studio configuration (currently automatic tax disabled); never silently switch tax behavior. Obtain explicit authorization before creating a live charge. Hosted billing gives eligible new organizations a 14-day no-card trial even with an empty offer catalog. Leave hosted billing off for local and self-hosted defaults.
- Stripe Checkout success redirects are not proof of payment. Preserve verified duplicate-safe webhooks, exact immutable price-to-plan mapping, failure/cancellation enforcement and billing-management access after product access expires. Existing subscriptions retain their agreed terms.
- Self-hosting stays independent of hosted subscriptions. Keep local-only auth bypass constrained to local development; never weaken production verification to simplify testing.

# Product principles

- **Bulk by default.** Collection interfaces lead with selection and shared actions. Use the shared bulk selection control. Select the current page first, then offer the full matching count when there are more pages. Keep selections when moving between pages and apply the active organization, workspace and filters when expanding selection. Creating, editing, running, pausing and scheduling should work on batches; a single item is a batch of one, not the primary interaction model.
- Store question text once per workspace in `prompt_questions` and make the wording immutable after creation. To replace wording, delete the existing variants and create a new question. Keep engine settings and metadata editable. Link `prompt_engines` to the question and keep per-engine IDs for schedules, runs and bulk actions. Apply library filters to engine records and paginate by question ID.
- Lead Prompts with the question library. Use stable question links for **Answers** and **Engine settings**, and preserve the library scope when opening recorded evidence. Start new monitoring from **Create prompts**. Every unarchived prompt supports manual and scheduled collection. Only schedules carry an enabled state. The Schedules page manages existing schedules. Review exact variants before collection, skip existing matches by default, and keep save receipts and manual batches independent of library filters and changing prompt sets. Use a stable operation ID when saving and reuse the same receipt action on retry.
- Schedule bulk edits send only changed fields. Updating the first local time retains the remaining time slots. Apply migration `0025` before deploying saved receipts and batch progress.
- Tracking setup saves variants into one new or existing workspace set with the receipt. Choose save-only, one-time or recurring collection before review. Keep an immediate first check unchecked for recurring setup. Existing matches join the set and are excluded from new collection unless the user opts in to exact reviewed IDs. Preserve existing active and paused schedules.
- Use progressive disclosure. Keep common tasks simple. Put location/language overrides, execution details, repeated samples and extra daily time slots under Advanced, with visible defaults and estimated total runs.
- Keep editable counts as drafts while typing. Validate whole-number bounds before enabling the affected action. A blank optional bulk field preserves existing values.
- Repeated samples are independent provider requests with distinct identities. Retries must be idempotent and must never quietly resubmit uncertain/accepted provider work.
- Explain Organization (team/billing/credentials) → Workspaces (client/brand/campaign folders) → Prompts, with multiple tracked brands per workspace. Use the sidebar workspace selector for scope across the app. `All workspaces` covers the organization. `Default workspace` is a regular workspace.
- Default poisoned-SERP fixing on for Google. Preserve organic blue links separately from AI Overview evidence.
- Trial onboarding: 14 days, no card or automatic charge. Payment is requested explicitly afterward. Existing Stripe subscriptions keep their agreed schedule. The owner authorized live launch of the three-tier catalog.

## Billing-account boundary

Migration `0022` replaces `billing_customers` with `billing_accounts` in a coordinated maintenance cutover. New organizations receive a stable account automatically; one organization owns one account and at most one subscription. Never use employee identity/email as the payer boundary or adopt Stripe metadata as ownership. `billing-account.ts` controls delegated billing permission independently of workspace roles. Only interactive owners can grant/revoke billing admins, in bulk; membership deletion cascades grants. REST/MCP reads and verified app handoffs remain available with paused product access; API keys cannot receive Stripe bearer sessions or mutate billing permissions. Commercial plan revisions and custom enterprise allowances do not grant organization roles. See `STRIPE_INTEGRATION_TODO.md` for remaining acceptance steps.

Launch authorization: Edwin explicitly instructed “make everything live, this IS a launch.” Enable all three production offers after migration/deployment. Treat tax policy as reviewed and complete; apply the supplied automatic-tax-off configuration. Do not silently revert to the older checkout pause or tax-gating policy. No real-card charge is authorized by this instruction alone.

## Public source and pricing presentation

The MIT repository is public. Contributions use forks/PRs and issues, not direct default-branch pushes. `main` requires the `check` CI job and a CODEOWNER review from `@eninodel`, with stale reviews dismissed and administrators included; no force pushes, deletion or bypass actors. Never weaken protection to merge an agent-authored PR. Owner review is a real human gate once protection is enabled.

Homepage and `/pricing` must reuse the live offer catalog and shared pricing component. All product features, seats and operational rate limits are the same across hosted tiers; only run allowance/searchable history differ. Higher-volume/longer-history inquiries go to info@trackrank.ai. Keep provider charges and search-window (not deletion) semantics explicit. Compare dated official competitor packages without fabricated prices, currency conversions, feature equivalence or guaranteed savings. Calculator defaults are labeled assumptions, not quotes. Light mode is the default unless the user explicitly selected dark. Trial countdowns use current-org billing state, are sticky/nondismissible, and direct users to existing authorized billing controls. These presentation changes reuse existing REST/MCP billing/offer/trial data and introduce no new privileged action.
